# Phase 0 Research: Task Detail Tabs & Completion Indicators

No `NEEDS CLARIFICATION` markers exist in the Technical Context — every decision below came from reading the current `TaskDetailModal.jsx`/`SupportIssueExtraFields.jsx`/`TaskComments.jsx`/`TaskFiles.jsx` (as they exist after 009-support-ops-knowledge-base's `readOnly` addition) and confirming actual usage across all four callers, not from the 2026-07-23 deferral note alone.

## Decision: whether a task shows 5 tabs or 3 is decided from `task.work_type`, not from which page opened it

**Rationale**: `work_type` is a real column already present on every `DetailedActivity`, already serialized on every payload this modal ever receives (raw model JSON for Kanban's tasks, `SupportIssueResource`/`TodaySupportIssueResource` for Support Ops issues) — it defaults to `'project'` and is only ever set to `'support'`/`'learning'` through `SupportOpsController::store()`'s intake flow. Confirmed via `grep` that `Kanban.jsx` never references `work_type` at all, so a Kanban-created task can never carry a Support Ops value. Keying the tab split off this existing column means `TaskDetailModal` decides its own tab count from the task it's showing, and every calling page — including any future one — gets correct behavior automatically, with no per-page flag to remember to set.

**Alternatives considered**: A boolean prop each caller passes explicitly (e.g., `isSupportIssue`) — rejected; it duplicates information the task object already carries, and a caller could pass the wrong value for a given task (e.g., forget to flip it when a list mixes work types) in a way `work_type` itself cannot be wrong about.

## Decision: `extraFields` is replaced by two render props, `supportFields` and `resolutionFields` — not one prop returning a two-part structure

**Rationale**: Today's single `extraFields(form, setForm, readOnly)` renders one blob (all of `SupportIssueExtraFields`) inside the Details tab's form — this *is* the "single long-scroll" problem this feature exists to fix. Splitting it into two named render props, each mounted as its own tab's body, is the direct, minimal change: `TaskDetailModal` shows the 5-tab layout only when **both** `task.work_type` is eligible **and** both `supportFields`/`resolutionFields` are supplied — a defensive double-condition, so a future support-work-type task passed to a caller that forgot to supply them never renders an empty or broken tab; it simply falls back to 3 tabs.

**Alternatives considered**: One `extraFields` prop returning `{ support: <jsx>, resolution: <jsx> }` — rejected as a distinction without a difference from two named props, just with a less self-documenting call site. A generic caller-defined dynamic-tab array (`tabs: [{key, label, render}]`) — rejected as the exact "fully general tab system" the original 2026-07-23 deferral named as a hard blocker and this spec's Assumptions deliberately avoid; nothing here needs more than the two fixed tabs this feature defines.

## Decision: `SupportIssueExtraFields.jsx` is split into two components along the same line as the tabs — `SupportIssueExtraFields` (narrowed) and a new `ResolutionExtraFields`

**Rationale**: The current single component already cleanly separates its own internal state by generator (Client Message Templates' and Freeform Client Update's state never touches the Troubleshooting Packet's state, and vice versa) — the fields FR-004 assigns to Support (Client, Tenant, Channel, Client Priority, Last Client Update, Next Action, plus the two client-communication generators) and the fields FR-005 assigns to Resolution (Evidence, Root Cause, Resolution, plus the Troubleshooting Packet generator) are already independent pieces of the existing component, not entangled ones. Splitting along this line is a mechanical decomposition of already-separable code, not a risky rewrite. Each new component keeps ownership of the field names it renders — `TaskDetailModal` never needs to hardcode `client_name`/`root_cause` itself.

**Alternatives considered**: Keep one component, have it internally render into two React portals/fragments passed back to the modal — rejected as needless indirection for what a plain two-component split already achieves cleanly.

## Decision (found during task planning): extract `GeneratorPanel`/`hasUnsavedFieldChange` into a new shared `SupportGeneratorPanel.jsx` before splitting the file

**Rationale**: The decision above treats the Support/Resolution split as clean because each generator's *state* is already independent — true, but incomplete: `SupportIssueExtraFields.jsx` also defines two module-scoped helpers, `GeneratorPanel` (the presentational chrome all three generators render through) and `hasUnsavedFieldChange(form, issue, fields)` (the shared "unsaved edit" warning check), and **neither is exported**. All three generators — including the Troubleshooting Packet generator this split moves to `ResolutionExtraFields.jsx` — use both today. Left alone, the split forces an unstated choice between duplicating both in the new file (real drift risk: the two files' generator chrome or warning logic could silently diverge the first time either is edited) or having `ResolutionExtraFields.jsx` reach into a sibling module's private internals, which isn't even possible without exporting them anyway. Extracting both into a new, shared, exported file closes this cleanly — a pure move, zero behavior change, with both `SupportIssueExtraFields.jsx` and `ResolutionExtraFields.jsx` importing from one place instead of one file quietly needing something the other privately owns.

**Alternatives considered**: Duplicate `GeneratorPanel`/`hasUnsavedFieldChange` in `ResolutionExtraFields.jsx` — rejected; it's exactly the kind of avoidable two-copy drift this session's own conventions (e.g., `isFilled` being defined once and reused by every consumer, not redefined per-file) already argue against elsewhere in this same spec. Leave `hasUnsavedFieldChange` un-shared (a local copy) while still extracting `GeneratorPanel` — considered as a smaller-footprint option, since `hasUnsavedFieldChange` is a tiny, four-line pure function; rejected in favor of sharing both from the same new file, since there's no cost to sharing it and doing so avoids a future editor needing to remember that *one* helper is shared while the *other* isn't.

## Decision: completion counts are computed by two small, exported pure functions co-located with the components that own the field names

**Rationale**: `getSupportCompletion(form)` (exported from `SupportIssueExtraFields.jsx`) and `getResolutionCompletion(form)` (exported from `ResolutionExtraFields.jsx`) each return `{ complete, total }` by checking exactly the fields FR-006/FR-007 name. `TaskDetailModal` imports and calls both (only when the 5-tab layout applies) to render the tab-label counts — it needs to call them, but never needs to know the field names itself, keeping the domain knowledge in one place per field group. Because completion is a pure function of `form`'s current values (which `TaskDetailModal` already holds as state), no new count-lifting mechanism is needed — unlike Comments/Files' `onCountChange` callback pattern, which exists only because *those* counts come from a separate API call the modal doesn't otherwise make.

**Alternatives considered**: Passing completion state up via a callback prop, mirroring `onCountChange` — rejected as unnecessary; that pattern exists to solve "child fetched something the parent doesn't have," which doesn't apply here since the parent already owns `form`.

## Decision: the tab-label completion count and the Comments/Files activity-count badge share their pill styling, but a persistent label-text difference keeps them from being confused (FR-009)

**Rationale**: `Support 2/2` and `Comments 3` need to read as different *kinds* of information at a glance — one is "how much of this is filled in," the other is "how much activity exists here." Reusing the exact same pill markup (already established: `<span className="ml-1 text-[10px] bg-primary/15 text-primary px-1.5 py-0.5 rounded-full font-bold">`) keeps visual consistency with the rest of the tab bar, while always rendering completion as an explicit `x/y` fraction (never a bare count) is what makes the two unambiguous without needing a second color, icon, or style — a bare "2" could be either kind of number; "2/2" can only be a completion count.

**Alternatives considered**: A different color or icon for the completion pill — rejected as an unnecessary visual-design addition when the fraction format alone already fully disambiguates the two without adding a new style to maintain.

## Decision: a save with missing required fields still saves, but the modal does not auto-close — it shows an in-modal summary instead, closable like everything else

**Rationale**: FR-011/FR-012 and Acceptance Scenario 2 require the save to succeed regardless and the summary to never be "a blocking confirmation the user must dismiss to proceed." But `TaskDetailModal` today auto-closes on any successful save (`if (result !== false) { onClose() }`) — if that behavior were left unchanged, an in-modal summary would never be visible long enough to read. The resolution: `handleSubmit` still calls `onSave(form)` exactly as today, and the save's success/failure handling is unchanged; the only new behavior is that if `getSupportCompletion`/`getResolutionCompletion` report anything missing at the moment of submission, the modal does not call `onClose()` afterward — it shows the summary and waits for the user to close it themselves (an ordinary explicit action, not a modal-blocking confirmation step). A save with nothing missing behaves exactly as it does today, auto-closing immediately.

**Alternatives considered**: A toast routed through the caller's existing `showToast` (the pattern `SupportOps.jsx`/`TodayDashboard.jsx` already use for other messages) — rejected; it would require a new callback prop threaded through every caller for a summary that's really about *this specific form's* current state, which the modal already has everything it needs to compute and display itself, self-contained, with no new prop surface.

## Decision: no backward-compatibility shim for the old single `extraFields` prop — all three current callers are updated in the same change

**Rationale**: `extraFields` has exactly three call sites, all within this codebase, all updated in the same commit as the prop rename — matching this project's own stated preference (per its working conventions) for changing call sites directly over keeping a deprecated alias with no real second consumer to protect. Kanban.jsx is unaffected either way, since it never supplied `extraFields` to begin with.

**Alternatives considered**: Keep `extraFields` accepted alongside the two new props for a transition period — rejected; there's no external consumer of this component and no phased-rollout need, so a shim would be pure, unnecessary complexity.

## Finding: this feature must account for 009's `readOnly` mode, which did not exist at the original 2026-07-23 deferral

**What was found**: 009-support-ops-knowledge-base added a `readOnly` prop to `TaskDetailModal`/`SupportIssueExtraFields`/`TaskComments`/`TaskFiles` after this redesign was first deferred. FR-014 already specifies the behavior (tabs and completion counts still show; field markers and the save-time summary do not apply) — this note records the concrete mechanics: `getSupportCompletion`/`getResolutionCompletion` still run and still populate tab labels in `readOnly` mode (harmless — they only read `form`, never gate anything else), but the per-field asterisk marker and the save-time summary banner are both conditioned on `!readOnly` (there being no `handleSubmit` path to reach in that mode at all, since the Save button already doesn't render there per 009).

**Output**: All Technical Context unknowns resolved via direct inspection of existing code; no `NEEDS CLARIFICATION` markers remain. Proceeding to Phase 1.
