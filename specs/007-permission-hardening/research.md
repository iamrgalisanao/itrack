# Phase 0 Research: Permission Hardening

No `NEEDS CLARIFICATION` markers exist in the Technical Context — every decision below came from reading existing code (`Project.php`, `DepartmentGrant.php`/`DepartmentGrantController.php`, `HasRole.php`, `AuditLogger.php`, `routes/api.php`, all six nested-resource controllers, `RoleAccessTest.php`, `frontend/src/lib/api.js`, `frontend/src/context/AuthContext.jsx`, `frontend/src/App.jsx`'s three Guard components) and the two architect-review rounds' own findings, not new research after the fact.

## Finding: the real FR-003 surface is six controllers with zero project-level authorization, not a department-vs-assignment tweak

**What was found**: `ProjectController` (index/show/dashboard) and `ReportController` already call `Project::accessibleTo($user)`. Every other project-nested controller — `ModuleController` (the actual data source for the Kanban board — there is no dedicated Kanban route), `ActivityController`, `SubActivityController`, `DetailedActivityController`, `CommentController`, `AttachmentController` — has **no project or department check at all**, only role checks (`canWrite()`/`isPmOrAdmin()`) that don't look at *which* project the target resource belongs to. Today, a Team Member in Department A can already read (and where role permits, write) a Department B project's modules/activities/tasks/comments/attachments purely because Laravel's route-model binding resolves the parent by ID with no ownership check.

**Implication**: this feature isn't primarily "narrow department to assignment" — it's "add project-level authorization to six controllers that currently have none, using the assignment model as the Team Member/Client scoping rule." Sizing and risk in plan.md reflect this.

## Decision: One trait (`BelongsToProject`), not six per-controller checks or a Policy class per model

**Rationale**: All six affected models sit at different depths under `Project` (`Module belongsTo Project` directly; `Attachment` is four levels down through `DetailedActivity → SubActivity → Activity → Module → Project`). A trait requiring each model to implement `resolveProjectId(): int` (walking its own specific relationship chain) and providing one shared `isAccessibleTo(User $user): bool` — delegating to the same `Project::scopeAccessibleTo` the top-level controllers already trust — means there is exactly one authorization rule, expressed once, regardless of nesting depth. `docs/prd_v2.md`'s own Technical Considerations already named this exact intent ("Existing `Project::accessibleTo(User)` should become the central access gate... all report, schedule, Gantt, Kanban... must use shared access logic") — this satisfies that at the design level without inventing a second, parallel mechanism (e.g., a Laravel Policy class per model) that would just be six more places to keep in sync with each other.

**Alternatives considered**: A Laravel Policy per model (`ModulePolicy`, `ActivityPolicy`, ...) — rejected; Policies are Laravel's idiomatic mechanism for per-action authorization, but here every model's rule reduces to the exact same question ("does this resource's project satisfy `scopeAccessibleTo`?") — six Policy classes duplicating that call is the multiplication risk the trait avoids, not less complexity. A single service method taking any model and switching on its class — rejected; the trait keeps the "how do I find my project id" logic co-located with the model that owns that relationship chain, rather than a central switch statement that has to be extended every time a new nested model type is added.

## Decision: `Project::scopeAccessibleTo`'s Team Member/Client branch checks `project_assignments`, not `department`

**Rationale**: Direct, minimal change — one `whereHas('assignments', fn ($q) => $q->where('user_id', $user->id))` replacing the current `where('department', $user->department)` for exactly the two roles named in FR-003. Admin/Project Manager (unrestricted) and Department Head (`DepartmentGrant`-based) branches are untouched — FR-004's "no change" requirement is structurally guaranteed by editing only the branch that applies to Team Member/Client, not by a separate regression check.

**Alternatives considered**: A parallel, separate scope (`scopeAssignedTo`) used only by the six newly-guarded controllers, leaving `scopeAccessibleTo` untouched for `ProjectController`/`ReportController` — rejected; this would mean two different authorization rules for the same two roles depending on which controller happens to be handling the request, precisely the drift risk FR-003's "enforced identically everywhere" language exists to prevent.

## Decision: Preview mode's effective-user resolution is one service (`AccessContext`), not a change to what `$request->user()` returns

**Rationale**: Sanctum's authenticated subject must stay the real Admin throughout a preview session — audit logging (`AuditLogger::record()` derives `actor_*` from `$request->user()`) must always attribute actions to the actual Admin, never silently to the previewed target, and the write-blocking check (FR-007) needs to know the *real* actor is an Admin currently previewing, not "believe" it's a Team Member with no write rights for an unrelated reason. Swapping `$request->user()` itself (e.g., via a custom guard) would blur this distinction and risk write-blocking being bypassed or misattributed. Instead, `AccessContext::user(Request $request): User` is the one call site every *read*-scoping check (the `BelongsToProject` trait, `scopeAccessibleTo` callers, the dashboard/report aggregations) uses in place of `$request->user()` — it reads whichever user `ResolvePreviewSession` middleware already resolved and attached to the request (the preview target if a valid session was presented, else nothing), falling back to the real authenticated user when nothing was attached (see the dedicated decision below on why validation itself lives in that middleware, not in `AccessContext`). Writes and audit logging never call `AccessContext` — they always use the real `$request->user()`.

**Alternatives considered**: A custom Sanctum guard/multi-auth setup that actually re-authenticates as the target — rejected as introducing real identity-switching machinery (session/token handling for a second identity) for a read-only feature that doesn't need it, and a much larger deviation from Principle VI's "one real auth path" than a single service call.

## Decision: Preview sessions are DB-backed opaque tokens with a 2-hour bounded lifetime, not JWTs or unbounded server sessions

**Rationale**: A preview session only ever *narrows* the previewing Admin's own already-authenticated access — it grants no one anything they don't already have, so the token doesn't need cryptographic self-verification (a JWT) the way an actual credential would; a plain random string (`Str::random(64)`, mirroring how `department_grants.granted_by_user_id` already opts for a plain column over a heavier mechanism) looked up in `preview_sessions` gives the one property that matters here: **instant server-side termination** — FR-019 requires a preview session to end immediately when the target's role changes or account is disabled, which a self-contained signed token (valid until its own expiry, unrevocable without a blocklist) can't do without extra machinery a DB row already gives for free. Every request presenting the token is validated fresh by `ResolvePreviewSession` middleware against the *current* target row (`is_active`, and role compared against `target_role_at_start`, a snapshot column added specifically so a role change — not just a disable — is detectable, per round-3 review) — never a value cached at session start, so a mid-session disable/role-change is detected on the very next request (FR-019) without a background job or webhook. A fixed 2-hour `expires_at` (set once, at start) satisfies FR-020's "bounded lifetime" without needing a sliding-expiration/renewal flow — 2 hours comfortably covers a single verification pass (SC-003 targets under 30 seconds per check) with room for an Admin to check several roles in one sitting.

**Alternatives considered**: A signed, stateless token (JWT) carrying the target user id and an expiry — rejected; can't be revoked before its own expiry without a server-side blocklist, which is the same DB-row bookkeeping this decision already requires, just with added token-verification complexity for no benefit given the low stakes of what the token grants. Unbounded sessions ended only by explicit action — rejected outright by FR-020.

## Decision: Preview session carried via `X-Preview-Session` request header, not a cookie or a query param

**Rationale**: The token narrows the *already-authenticated* Admin's session (Sanctum's own cookie remains the actual auth mechanism, unchanged) — a second, independent header keeps preview state orthogonal to authentication, and is trivially attachable via one `axios` request interceptor addition in `frontend/src/lib/api.js` (which today has a response interceptor only, no request interceptor — this is new but minimal). A cookie would conflate two concerns in one transport mechanism and complicate the "same tab only, sessionStorage-scoped, gone if the tab closes" semantics FR-020's bounded-lifetime spirit implies; a query param would leak the token into server access logs on every single request.

**Alternatives considered**: Storing preview state server-side keyed only by the Admin's Sanctum session (no client-visible token at all) — rejected; would mean at most one active preview per Admin *session* with no way for the client to know if that state is still valid without an extra round trip, whereas an explicit token the client already holds lets `ResolvePreviewSession` validate and respond in the same request that needed the data anyway.

## Decision: Preview validation is a dedicated middleware (`ResolvePreviewSession`) that runs before any controller, not logic inside `AccessContext`

**Rationale (revised after round-3 review point 3)**: An earlier draft had `AccessContext::user($request)` do the token lookup and validity check itself, falling back to the real Admin's own data if the presented token turned out to be invalid. That's a correctness trap: by the time a controller has called `AccessContext::user()` deep inside a read-scoping check, it's often already partway through building a response — falling back "in place" risks a single response that mixes an `X-Preview-Ended` signal with real, unrestricted Admin data rendered into a screen the Admin still perceives as a read-only preview of someone else's narrower view. Moving validation into `ResolvePreviewSession` middleware — which runs first in the authenticated group, before `BlockWritesDuringPreview` and before any controller — means an invalid token never reaches a controller at all: the middleware short-circuits with `409` and no domain data whatsoever, and only a subsequent, separate request (issued by the frontend after it clears local state) ever gets real data, under whichever identity actually applies to *that* request. `AccessContext` is left as a two-line accessor with no lookup logic or side effects, safe to call from anywhere with no risk of the fallback-mixing problem, because the middleware has already guaranteed that if a controller is running, any presented token was valid at that moment.

**Alternatives considered**: Keeping validation inside `AccessContext` and having every controller explicitly check for and handle an "invalid preview" signal before proceeding — rejected; reintroduces exactly the "six/eight places to keep in sync" risk this feature's other primitives (`BelongsToProject`, the exception-handler rule) were built to avoid, for a check that's naturally a single request-lifecycle gate.

## Decision: Starting a new preview session (`POST /api/preview-sessions`) is exempt from `BlockWritesDuringPreview`

**Rationale (round-3 review point 1)**: The frontend attaches `X-Preview-Session` to every request while a preview is active, including the request to *replace* that preview with a new one. Without an exemption, `BlockWritesDuringPreview` would reject the very `POST` that's supposed to end the old session and start a new one, since it's a non-GET request carrying a currently-valid preview token — a real deadlock the original design missed. `PreviewSessionController::store` already ends any prior session for the acting Admin before creating the new one (data-model.md), which is what actually makes allowing this write safe: it's not an arbitrary mutation slipping through preview mode, it's the one specific action whose entire purpose is managing preview state itself, analogous to how `DELETE /api/preview-sessions/current` was already exempt for the same reason.

**Alternatives considered**: Requiring the frontend to call "end preview" before "start preview" as two separate round trips, keeping the middleware exemption-free — rejected; adds a real race window (a request in between the two calls would see no active preview and get the Admin's own full data) for no benefit over a same-request replace that the controller already implements atomically.

## Decision: Role-based endpoint gating always evaluates before project-assignment scoping — and, during preview, evaluates against the *effective* user, not just the real one

**Rationale (round-3 review point 4, sharpened by round-4 review)**: `GET /api/reports/export-csv` already denies the Client role entirely, independent of this feature. Project-assignment scoping is additive narrowing for roles an endpoint already permits — it was never meant to, and must not, be read as *replacing* or *superseding* an existing role-based denial; that ordering (role gate, then assignment/project scoping) is unchanged and correct on its own. An earlier version of this decision claimed "no code change was needed" for this ordering to hold — true for a real, non-previewing user, but **wrong** for preview mode: FR-006 requires previewing as a Client to reflect exactly what a Client sees, including being denied the export endpoint. If `ReportController::exportCsv`'s `$user->isClient()` check keeps resolving `$user` from the real Sanctum session, an Admin previewing as a Client would *not* see that denial — they'd see the Admin's own (unrestricted) export access, which is exactly backwards from what preview mode promises. The check's own logic is unchanged; what changes is *which user* it evaluates — see the next decision for the actual mechanism.

**Alternatives considered**: Leaving pre-existing role checks resolved against the real user and treating "role checks aren't preview-aware" as an accepted limitation — rejected; FR-006 doesn't say "project assignments are previewed, other role behavior isn't" — it says the Admin sees exactly that user's access, full stop. Silently narrowing FR-006's scope to only the assignment dimension would be a spec violation, not a simplification.

## Decision: Every project-scoped controller's existing private `user()` helper is repointed to `AccessContext::user()` — not a new call site added to each individual check

**Rationale (round-4 review)**: Every controller in this codebase already has an identical private helper — `private function user(Request $request): User { return $request->user(); }` — and every role/authorization check inside that controller calls `$this->user($request)` rather than `$request->user()` directly (confirmed via `grep` across all 15 controllers that define it; `ProjectController`, `ModuleController`, `ActivityController`, `SubActivityController`, `DetailedActivityController`, `CommentController`, `AttachmentController`, and `ReportController` are the eight this feature's read paths touch). Changing that one line, in exactly those eight controllers, to `return AccessContext::user($request);` makes **every** check in that controller — the new `BelongsToProject`/`scopeAccessibleTo` checks *and* every pre-existing role check (`ReportController::exportCsv`'s Client denial, `DetailedActivityController`'s `client_visible` filtering, etc.) — resolve against the effective (possibly previewed) user automatically, with zero changes to the individual `$user->isClient()`/`$user->isTeamMember()` call sites themselves. This is the same "one primitive, not N call-site edits" reasoning this plan already applied to `BelongsToProject` and the exception-handler rule, just applied to a seam that turned out to already exist in the codebase rather than one this feature has to introduce.

Write methods (`store`/`update`/`destroy`) also call `$this->user($request)` and would therefore also resolve to the preview target if this were reachable during an active preview — but `BlockWritesDuringPreview` already rejects every non-GET request under an active preview session before any controller method runs (research.md's write-blocking decision), so those call sites are provably unreachable during preview regardless of what `$this->user()` would return. No special-casing is needed to keep writes on the "real user" — they simply never execute far enough to matter.

**Scope discipline**: only the eight controllers this feature's project-scoped reads touch are changed this way. `AuditLogController`, `DepartmentGrantController`, `TeamMemberController`, `NotificationController`, `GlossaryTermController`, `SupportOpsController`, and `UserManagementController` also define the identical helper but are **not** touched — none of them are project-scoped resources FR-006 promises preview coverage over, and repointing them would be unscoped, unrequested behavior change to Admin-only tooling that has nothing to do with "see what a Team Member/Client/Department Head sees."

**Alternatives considered**: Adding `AccessContext::user($request)` as a new, separate call at each individual role-check site (`$user->isClient()` → `AccessContext::user($request)->isClient()`), leaving each controller's `$this->user($request)` calls and their real-user semantics untouched — rejected; this is the "eight controllers × several call sites each" duplication risk the trait/primitive pattern elsewhere in this plan was built to avoid, for no benefit over changing the one shared helper each controller already funnels through.

## Decision: Preview start rejects a disabled target account up front, not only via later mid-session detection

**Rationale (round-3 review high-priority item)**: `ResolvePreviewSession`'s `invalidReason()` check already detects a target becoming disabled *during* a session (FR-019) — but nothing previously stopped `PreviewSessionController::store` from creating a session whose target was *already* disabled at creation time, which would immediately be invalid on its very first use. Adding the same `is_active` check to `store`'s validation (alongside the existing "not an Admin" check, FR-009) rejects that case with a clear `422` at creation, rather than letting an Admin start a preview that fails confusingly on the next request.

**Alternatives considered**: Relying solely on the mid-session check to catch this — rejected; technically "works" (the very next request would 409) but is a worse experience than failing clearly at creation, and there's no reason not to check something already known at `store` time.

## Decision: Non-enumeration (FR-005/FR-011) is one exception-handler rule, scoped to Team Member/Client requesters only

**Rationale**: Laravel's implicit route-model binding already throws `ModelNotFoundException` → 404 for a genuinely nonexistent ID *before* any controller code (or the `BelongsToProject` check) runs — so an existing-but-inaccessible project already gets 403 (from the trait check) while a nonexistent one gets Laravel's default 404, exactly the distinguishable-response gap FR-011 forbids. Rather than rewriting all six controllers' route parameter resolution to do manual lookups (turning every `show`/`update`/`destroy` into hand-rolled `find()`-or-403 code, in six controllers, six times), one addition to the exception handler maps `ModelNotFoundException` for the seven project-chain model classes (`Project`, `Module`, `Activity`, `SubActivity`, `DetailedActivity`, `Comment`, `Attachment`) to the same 403 shape the trait's own denial uses — but **only** when `AccessContext::user($request)` is a Team Member or Client. Admin/PM/Department Head keep Laravel's default 404 for a truly missing ID, which is correct and unchanged (FR-004) — non-enumeration only matters for the two roles this feature actually narrows; those roles already saw their whole department before, so there's no new information-leak risk being introduced for the broader roles by leaving their behavior as-is.

**Alternatives considered**: Rewriting every controller's `show`/`update`/`destroy` to do explicit `Model::find($id)` instead of relying on route-model binding — rejected; six controllers' worth of mechanical rewrites for what is, in the end, one rule ("missing or inaccessible → same 403, for these two roles"), better expressed once. Applying the 404→403 remap to *every* role — rejected; would be a real, unjustified behavior change for Admin/PM/Department Head, violating FR-004 for no requirement that asks for it.

## Decision: Writes during preview are blocked by one global middleware, not a per-controller check

**Rationale**: `BlockWritesDuringPreview`, added to the same `['auth:sanctum', EnsureUserIsActive::class]` group in `routes/api.php` that 006 already established as this app's one place for cross-cutting authenticated-request gates, rejects any non-`GET` request when a valid preview session is active for the requester — before any controller runs. This guarantees FR-007 holds for every current *and future* mutating endpoint automatically, the same reasoning 006 used for `EnsureUserIsActive`'s placement, rather than adding an `if (previewing) abort(403)` line to every controller's every write method (a line that a future new endpoint could simply forget to add).

**Alternatives considered**: A per-controller check — rejected for the same "a future endpoint could forget it" reason 006 rejected a per-controller disabled-account check.

## Decision: Assignment target validation reuses `HasRole`/`is_active`, no new role-list literal

**Rationale**: FR-016 (only Team Member/Client, only active accounts, may be assignment targets) is validated in `ProjectAssignmentController::store` via `$targetUser->isTeamMember() || $targetUser->isClient()` and `$targetUser->is_active`, mirroring `DepartmentGrantController`'s existing validation style — never a second hardcoded role-name list (the exact drift risk 006's research.md already flagged and avoided for its own role validation).

**Alternatives considered**: A `Rule::in([...])` literal role list on the request — rejected, same drift risk as any hand-typed role list elsewhere in this codebase.

## Decision: Assignment idempotency via a DB unique constraint plus `firstOrCreate`, not application-level duplicate checking

**Rationale**: `project_assignments` gets a unique index on `[user_id, project_id]` (mirroring `department_grants`' own composite-unique precedent). `ProjectAssignmentController::store` uses `firstOrCreate` — if the pair already exists, the existing row is returned and **no** audit entry is written (FR-017's "no duplicate audit entry"); if it's new, one row and one `project_assignment.created` audit entry are written. The unique index is the actual correctness guarantee under concurrent requests; the `firstOrCreate` call is what keeps a duplicate attempt from surfacing as a 500 (constraint violation) instead of the idempotent 200/201 FR-017 calls for.

**Alternatives considered**: An application-level `where(...)->exists()` check before insert with no DB constraint — rejected; leaves a race window between the check and the insert, the same class of bug 006's research.md flagged for the last-enabled-Admin invariant (there solved with a locked transaction; here solved more simply because uniqueness is a static property of the row, not a dynamic count that changes based on concurrent state — a unique index alone is sufficient).

## Decision: `project_assignments`/`preview_sessions` foreign keys are real, constrained `foreignId()`s — not a repeat of `department_grants.granted_by_user_id`'s unconstrained-column pattern

**Rationale**: `department_grants.granted_by_user_id` was found to have no FK constraint at all (a plain nullable `unsignedBigInteger`) — a pre-existing gap, not a pattern worth repeating. Both new tables' user/project references use proper `foreignId(...)->constrained()`, giving referential integrity and, for `project_id`, the `cascadeOnDelete()` FR-014 needs "for free" (see next decision) rather than relying on manual cleanup code.

**Alternatives considered**: Matching `department_grants`' existing unconstrained-column style for consistency — rejected; that pattern is a gap this feature has no reason to propagate, and the new tables benefit directly from real constraints (cascade delete, no orphaned rows even if application code has a bug).

## Finding: FR-014 (cascade-delete assignments when a project is deleted) needs zero new application code

**What was found**: `ProjectController::destroy()` calls `$project->delete()` with no manual cascade logic anywhere in the controller or a model observer — the entire existing Project → Module → Activity → SubActivity → DetailedActivity → Comment/Attachment chain cascades purely through `->cascadeOnDelete()` foreign keys declared in each child table's migration. Giving `project_assignments.project_id` the same `->cascadeOnDelete()` (previous decision) means FR-014 is satisfied by the migration alone — one `DELETE` on `projects` and MySQL's own FK cascade removes the assignment rows, identical to how every other child table already behaves. No new observer, event, or controller code is needed.

**Note, not a requirement of this feature — flagged as a follow-up backlog item, not to be silently lost**: the same investigation found that `AttachmentController::destroy()` is the *only* place that deletes an attachment's physical file from disk (`Storage::disk(...)->delete(...)`) — a project-level cascade delete never touches disk, so deleting a project with attachments already leaves orphaned files today, unrelated to and unaffected by this feature. Not in scope for 007; recorded here so a future cleanup (e.g. a `deleting` model event on `Project` that walks its attachments and removes their files before the FK cascade removes the rows) has a starting reference instead of being rediscovered from scratch.

## Decision: Frontend — one shared `AccessDenied` component replaces three duplicated Guard-panel copies

**Rationale**: `KanbanGuard`/`SupportOpsGuard`/`AdminGuard` in `App.jsx` are three near-identical, independently hand-copied "Access Denied" JSX blocks (icon + heading + paragraph + back link), each gating a whole route by comparing `user.role` against a hardcoded allow-list. FR-010 requires a consistent access-denied experience across every entry point — the current three-copies-that-can-drift state is exactly what that requirement is against. A single `<AccessDenied />` component, parameterized only by an optional message, is used both by the three existing route Guards (reduced to a role check + the shared component) and, newly, by pages that fetch project-scoped data and receive a 403 mid-session (Dashboard/Schedule/Work Program/Reports currently show a generic toast on any fetch error, not an access-denied state) — giving FR-010 one real implementation, not an aspiration.

**Alternatives considered**: Leaving the three Guards as-is and only adding new handling for the project-scoped 403 case — rejected; would satisfy FR-010's letter for the *new* surfaces while leaving the pre-existing three-way duplication (and its drift risk) untouched, when consolidating costs little given how small each copy already is.

## Decision: Preview state lives in `sessionStorage`, not `localStorage`

**Rationale**: Preview is explicitly a transient, read-only verification tool (Story 2) — `sessionStorage`'s tab-lifetime scope means a closed tab or ended browser session leaves no lingering client-side preview flag to confuse a later, unrelated session, consistent with the bounded-lifetime spirit of FR-020 even though the *authoritative* expiry is always server-side (`preview_sessions.expires_at`, re-checked every request by `ResolvePreviewSession` — client-side storage choice is a UX nicety, never the enforcement mechanism).

**Alternatives considered**: `localStorage` — rejected; would survive tab/browser close, in tension with preview's transient nature, and the client-side value being stale is exactly one of the things `ResolvePreviewSession`'s per-request server-side re-check already has to handle regardless, so there is no correctness need for `localStorage`'s persistence.

**Output**: All Technical Context unknowns resolved via direct inspection of existing code; no `NEEDS CLARIFICATION` markers remain. Proceeding to Phase 1.
